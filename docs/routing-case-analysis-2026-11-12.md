# 이상 경로 원인 분석과 해외 지원 검토

조사일: 2026-11-12 (한국 시간). 운영 SSH 서버의 Trazo DB와 GraphHopper 9.1을 조회하고 저장된 마커 좌표로 재탐색했다. 대상은 실제 폴더명 `이상경로케이스`(ID 15)의 코스 170–174다. 코스 179는 사용자가 잘못 넣었다고 확인하여 분석 대상에서 제외했다. 운영 코드·설정·저장 코스를 변경하지 않았다.

## 검증 조건과 한계

- 운영 프로필: `run`, `distance_influence: 200`. 기본 옵션: `prefer_trails`, `avoid_big_roads`, `avoid_stairs`.
- 기본값, 옵션 없음, 페리 통행 금지, 거리 우선, 스냅 제한 제거를 비교하고 필요한 구간은 옵션 하나씩과 거리 가중치 500/1000으로 추가 비교했다.
- 서버 그래프의 `import_date`: `2026-11-10T19:03:30Z`; `data_date`: `2026-11-09T21:22:17Z`.
- 코스 170–174는 11월 10일 저장됐다. 생성 당시 옵션·원래 클릭 좌표·지도 버전이 코스에 보존되지 않으므로 당시의 요청을 완전히 복원할 수 없다. 아래 숫자는 저장된 마커로 현재 운영 엔진을 재탐색한 결과다. 옵션을 끈 비교도 기본 프로필 자체의 선호도는 유지한다.
- 고도 평활화는 위도·경도 우회 원인이 아니다. 경로 좌표는 GraphHopper가 만들고 프런트는 반환된 선을 저장·표시한다.

### 170: 이상하게 돌아감

2→3번 마커는 서초대로를 따라가는 대신 남쪽의 서초대로42길·반포대로30길로 빠진 뒤 돌아온다. `공원·산책로 우선`만 켜면 1,515.1m, `큰 차도 피하기`만 켜면 약 1,700m, `계단 피하기`만 켜면 1,489.8m다. 주된 원인은 큰 차도 회피이며 산책로 선호도 경로 선택을 바꾼다. 거리 가중치를 500/1000으로 높여도 기본 옵션을 유지하면 약 1,515m로, 옵션 없는 경로와 완전히 같아지지는 않았다.

`avoid_big_roads`는 PRIMARY/TRUNK의 우선도를 0.7배로, `prefer_trails`는 FOOTWAY 등의 우선도를 1.4배로 만든다. 짧은 큰길보다 길지만 선호하는 길이 더 낮은 비용을 갖게 된다. 1→2번 마커에서도 기본 379.5m 대 옵션 없음 360.4m로 작은 우회가 재현된다.

해결 방향은 큰 차도 회피를 선택 옵션으로 두거나 강도를 줄이고, 산책로 선호도 약하게 조정하는 것이다. 최단에 가까운 후보도 계산해 우회율이 큰 경우 대안을 제공하는 방법도 있다. 이때 비교 대상은 같은 통행 제한을 지키는 경로여야 한다.

### 171: 한강버스 경로

2→3번 마커 사이의 응답에 `한강버스 (급행)` 탑승 지시와 `road_environment=ferry`가 직접 들어 있다. 배를 타는 안내 구간만 약 9.84km다. 배제 규칙을 넣으면 육상 경로 10,297.3m가 반환되어 같은 두 점 사이를 배 없이 잇는 것이 가능함도 확인했다.

`backend/main.py`의 `snap_preventions`에 있는 `ferry`는 점을 붙일 도로 선택만 제한한다. 경로 중간에 배 노선을 통과하는 것은 막지 않는다. 현재 프로필에는 FERRY를 통행 불가로 만드는 규칙이 없고, 배의 이동 비용이 유리해 선택된다. 옵션을 모두 꺼도 그대로다.

검증한 해결 규칙은 `road_environment == FERRY`일 때 `multiply_by: '0'`이다. 러닝·자전거에 공통으로 배 이용 금지를 기본 적용하고 필요할 때만 별도 허용할 수 있다. 요청별 규칙으로 넣는 방식은 그래프 재생성 없이 이 사례에서 동작했다. 프로필 설정에 영구 반영하는 방식은 그래프와 프로필 변경 절차를 함께 확인해야 한다.

### 172: 불필요한 횡단보도 우회

잠원로의 마지막 부분에서 중앙 도로선을 계속 따라가는 대신 옆의 FOOTWAY로 빠져 돌아온다. `공원·산책로 우선` 하나만 켜도 1,115.0m가 재현되고, `큰 차도 피하기`만 또는 `계단 피하기`만 켜면 1,089.3m다. 이 사례의 직접 원인은 산책로 가산점이다. 거리 가중치 500으로도 1,089.3m 경로로 바뀐다.

다만 짧은 경로의 선은 OSM의 일반 도로 중심선이다. 이것이 실제로 보행자가 같은 쪽 보도로 계속 갈 수 있다는 현장 증명은 아니다. 현재 그래프는 '횡단보도를 한 번 덜 건너기'에 별도 비용을 주지 않는다. 선호도 완화로 이 우회는 줄일 수 있으나 보도 방향까지 정확히 안내하려면 연결 데이터와 횡단 비용도 모델링해야 한다.

### 173: 횡단보도 두 번째 사례

1→2번 마커는 약 1,051.1m로 옵션 유무에 관계없이 같다. 2→3번은 현재 약 478.3m이며 기본·옵션 없음·거리 우선·스냅 제한 제거·각 단독 옵션에서 모두 같은 경로다. 저장된 선은 약 503m이고 현재 결과와 다른 쪽 보도 선을 일부 사용한다. 따라서 현재 실험만으로 당시의 불필요한 횡단을 동일하게 재현했다고 말할 수 없다.

두 번째 마커는 잠원로 도로 중심선에 놓여 있고 이후 보행로로 이어진다. 현재 시스템은 양쪽 보도를 일관되게 선택하는 상태를 보관하지 않고 각 마커 사이를 별도 요청한다. 따라서 도로 중심선·보도 연결 구조와 스냅 선택을 검토해야 한다. 이 사례는 선호도 숫자 하나만 조정하면 해결된다고 보기 어렵다. 원본 클릭 위치와 연결 정보를 보존하고, 필요 시 같은 보도 쪽에 경유점을 놓거나 보도 기반 스냅을 제공하는 방향이 적절하다.

운영 PBF에서도 이 혼용을 확인했다. 잠원로 way `218870939`에는 `highway=secondary`, `sidewalk=both`가 있고, 바로 옆에 별도 `footway=sidewalk`와 `footway=crossing`이 있다. 저장된 173의 선은 교차로 중심 노드 `2244637657`을 거쳐 횡단보도 way `1211628009`와 북쪽 보도 `1497710470`으로 간다. 현재 선은 남쪽 횡단보도 `1211628008`의 중간 노드 `11225325967`에서 동쪽으로 빠져 남쪽 보도 `1576459847`로 간다. 이 남쪽 보도는 잠원로 접근 방향에서는 노드 `14357721608`에서 끝나는 불완전한 선이기도 하다. 즉 '보도 양쪽이 있다고 표시된 중앙 도로선'과 '별도로 그린 실제 보도/횡단보도'를 섞어 탐색하는 데이터 구조가 확인된다. 해당 끝점이 현장의 실제 단절인지, 매핑 누락인지는 현장/검증 가능한 자료 확인이 더 필요하다.

### 174: 서초역사거리

2→3번 마커에서 기본 옵션은 남쪽의 FOOTWAY를 여러 번 잇는 226.2m 경로를 선택한다. 옵션을 모두 끄면 도로 중심선을 사용하는 200.7m 경로다. 산책로 선호·큰 차도 회피·계단 회피를 각각 하나씩만 켰을 때도 200.7m이므로, 이 경우는 선호도와 회피 옵션의 조합이 경로 선택을 뒤집는다. 거리 가중치 500으로도 200.7m로 바뀐다.

보도와 횡단보도를 최우선으로 따를지, 큰길 중심선을 보행 가능한 길의 대략적인 표현으로 쓸지에 대한 모델의 일관성 문제도 있다. 단순히 모든 보행로를 강하게 선호하면 교차로에서 보도를 찾아 멀리 도는 경로가 나온다. 반대로 보행로 선호를 없애면 보기에는 곧지만 도로 중심선을 가로지르는 선이 생길 수 있다. 따라서 우회 억제와 실제 횡단 가능 여부는 나누어 검증해야 한다.

운영 PBF에서 기본 경로가 지나는 `845497276`, `845497277`, `845497285`는 실제로 `footway=crossing`으로 태깅돼 있다. 이들을 공원 산책로와 똑같은 `highway=footway`로 선호하는 현재 규칙은 횡단보도에도 1.4배 가산점을 준다. 따라서 단순한 화면 착시만은 아니며, 횡단보도를 산책로 선호 대상에서 구별하는 설계가 필요하다. 현재 encoded value에는 `footway=crossing` 자체가 없어서 이 구별을 제대로 구현하려면 import 시 인코딩/파서 확장이 필요할 수 있다.

[운영 OSM 기반 교차로 연결 비교 그림](routing-case-topology-2026-11-12.svg): 빨강은 현재 기본 옵션, 보라는 173의 저장된 선, 초록은 174의 옵션 없는 선이다. 주황은 OSM에 등록된 횡단보도다. 이는 OSM 그래프의 연결을 설명하는 그림이며 실제 도로 배치나 현재 통행 가능 여부를 보증하는 지도는 아니다.

## 공통 개선 순서

1. 러닝·자전거에서 페리를 명시적으로 차단한다. 이 문제는 원인과 대체 경로가 확인됐다.
2. 산책로 선호·큰 차도 회피의 기본 강도와 조합을 조정한다. 170/172/174를 함께 재검증하고 다른 도심·강변·산길 구간에 미치는 영향을 확인한다. 거리 가중치 500은 후보이며 전체 적용을 결정할 충분한 검증은 아직 아니다.
3. 클릭 좌표와 스냅 좌표, 종목·옵션·지도/프로필 버전을 코스에 보존한다. 현재는 마커 자체가 스냅된 좌표로 바뀌어 원래 클릭 의도를 추적하기 어렵다.
4. 도로 중심선과 별도 보도를 함께 사용하는 문제를 개선한다. 가까운 보도 후보, 진행 방향, 앞뒤 구간 연결을 고려한다. 잘못되거나 빠진 OSM 연결은 사실 확인 후 원본 지도 수정 또는 로컬 보정으로 처리한다.
5. 횡단보도/신호 대기·불필요한 왕복 비용을 모델링한다. 현재 `graph.encoded_values`와 프로필에는 이를 직접 나타내는 값이나 횡단 비용이 없다. 단순히 `road_class == FOOTWAY`로 횡단보도를 구별할 수는 없다.

## 해외 길찾기와 지도 전환

**둘 다 가능하다.** 현재도 한국의 길찾기는 카카오가 아닌 GraphHopper와 OSM이 담당한다. 한국은 카카오맵을 화면에 표시하는 구조다. 따라서 해외 OSM 데이터를 길찾기 엔진에 추가하고 화면용 지도를 별도 제공하면 된다. 해외 지도를 보여주는 것만으로 해외 길찾기가 생기지는 않는다.

### 길찾기 서버

현재 한국 PBF는 약 278MiB, 그래프는 약 389MiB다. GraphHopper Java heap은 2GiB, 컨테이너 한도는 3GiB다. 호스트는 총 약 15.3GiB 메모리를 여러 서비스가 공유하고 조사 시 available은 약 3.5GiB, swap은 전량 사용 중이었다. 이 상태에서 전 세계 그래프를 그대로 추가하는 계획은 적절하지 않다. 특정 도시·지역부터 별도 엔진으로 검증하거나 해외만 외부 길찾기 API로 처리하는 것이 현실적이다. 목표 지역별 실제 import·동시 요청 부하를 측정하기 전 필요한 RAM과 비용을 확정할 수 없다.

권장 구조는 `/route` 인터페이스를 유지하고 백엔드에서 좌표와 서비스 범위에 따라 한국/해외 엔진으로 보내는 방식이다. 독립된 국가 그래프는 국경을 넘는 경로를 자동으로 연결하지 못하므로, 국경 횡단이 필요한 권역은 연결된 데이터를 함께 import하거나 해당 범위를 지원하는 외부 API를 사용해야 한다. 지원 범위 밖은 명확히 안내한다. 현재처럼 모든 GraphHopper 오류를 일반 오류 하나로 바꾸면 범위 밖·연결 단절·타임아웃 구별도 어렵다.

`update-osm.sh`와 설정 파일은 한국 단일 파일·단일 그래프·서울 확인 좌표를 전제로 한다. 국가/권역별 데이터, 저장 경로, 배포 및 확인 좌표를 분리해야 한다. 현재 CH/LM이 없는 요청별 custom model 구조의 장거리 탐색 성능도 다시 측정해야 한다. 외부 API를 쓰면 해당 API가 러닝/자전거, 고도, 요청별 회피 옵션을 어느 범위까지 지원하는지 확인해야 한다.

한국용 프로필을 해외에 그대로 적용하면 품질과 통행 규칙 문제가 생길 수 있다. 특히 현재 자전거 프로필은 역방향 통행을 완전 금지가 아닌 0.7 감점으로 허용하고, 러닝 프로필은 국내 큰길에 보도가 흔하다는 가정으로 선호도를 보정한다. 해외에서는 지역별 규칙과 OSM 태그를 기준으로 재검증해야 한다. 고도 제공 범위와 누락 시 대체 처리도 점검 대상이다.

### 한국 카카오맵 / 해외 OSM 화면

한국용 카카오 렌더러와 해외용 OSM 기반 렌더러를 분리하고, 마커·경로·이벤트·화면 이동을 공통 인터페이스로 감싸면 가능하다. 해외 렌더러 후보는 MapLibre GL JS다. 코스 데이터는 이미 위경도와 고도로 저장되어 있어 기존 코스의 본질적인 좌표 형식은 재사용할 수 있다. 다만 지도 라이브러리별 좌표 순서·줌 수준·투영과 픽셀 좌표 변환은 어댑터에서 처리해야 한다.

지도 선택은 접속자 IP나 언어보다 **보고 있는 코스/편집 지역**을 기준으로 한다. 한국 사용자가 일본 코스를 계획할 수 있기 때문이다. 새 편집은 명시적인 지역 선택과 현재 위치를 사용하고, 저장/공유 코스는 코스 좌표로 결정한다. 넓게 축소한 화면이나 경계 지역에서는 전 세계 지도를 유지하는 등 전환이 반복되지 않도록 설계한다. 지원 경계는 위경도 사각형 하나보다 실제 국가/서비스 영역 폴리곤을 기준으로 판단하는 것이 정확하다.

현재 카카오 의존은 다음에 퍼져 있다.

| 기능 | 주요 위치 | 필요한 작업 |
| --- | --- | --- |
| 코스 편집·마커 이동·선택·지도 투영 | `frontend/src/App.jsx` | 렌더러 공통 인터페이스, SDK 지연 로딩과 실패 분리 |
| 공유 코스 지도 | `frontend/src/components/CourseMap.jsx` | 코스 위치에 따른 지도 선택 |
| 코스 탐색 | `frontend/src/components/CourseExplorer.jsx` | 해외 지도·범위 검색 지원 |
| 장소 검색 | `frontend/src/hooks/usePlaceSearch.js`, `PlaceSearch.jsx` | 한국 카카오/해외 검색 공급자 분리 |
| 이미지 저장 | `frontend/src/utils/courseImage.js` | 카카오 투영·타일 의존 교체, 해외 타일의 이미지 내보내기 허용/CORS 확인 |
| 공유 페이지 초기 로딩 | `backend/templates/course.html`, `frontend/src/landing/courseViewer.jsx` | 카카오 SDK 로드에 의존하지 않는 해외 초기화 |
| 지역 이름·MCP 장소 검색 | `backend/main.py` | 해외 reverse geocoding과 검색 지원 |
| 코스 주변 장소 분석 | `backend/osm_places.py`, insight worker | 한국 PBF 외의 자료 선택과 인덱스 전략 |

OSM은 데이터이며 화면 타일·길찾기·장소 검색은 각각 별도 서비스다. MapLibre를 설치해도 타일이나 검색 데이터가 자동으로 따라오지는 않는다. 운영 화면용 타일은 OSM 기반 공급자 또는 자체 호스팅을 선택해야 한다. OSM 표준 공개 타일은 무제한 서비스가 아니고 SLA도 없으며 출처 표시·캐시 등 사용 정책을 지켜야 한다. 검색 또한 운영 용량을 가진 공급자 또는 자체 호스팅으로 분리하는 편이 적절하다.

구현 순서는 해외 공유 코스 표시 → 해외 편집 지도와 검색 → 한 도시/권역의 길찾기 → 고도·이미지 저장·코스 분석까지 완성 → 대상 지역 확대가 적절하다. 표시만 가능한 지역과 실제 길찾기를 지원하는 지역은 UI에서 구별해야 한다.
