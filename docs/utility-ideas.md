# 트라조 유틸리티 확장 아이디어

2026-11-12 기준 `/utility`의 구현을 확인했다. 러닝 페이스·완주 시간·거리 계산 외에 400m/200m 랩, 1km 누적 스플릿, 리겔 예상 기록이 이미 있다. 자전거 탭은 준비 중이다. 이미 제공하는 계산을 새 도구처럼 중복 추가하기보다 **만든 코스를 실제 운동에 쓰는 과정**을 연결하는 것이 적합하다. 아래는 구현 제안이며 이번 변경에 유틸리티를 실제 추가한 것은 아니다.

## 먼저 만들 후보

| 우선순위 | 도구 | 입력 → 결과 | 트라조와 연결 | 외부 비용 |
| --- | --- | --- | --- | --- |
| 1 | 인터벌·런워크 구성기 | 워밍업, 운동/회복 거리·시간, 반복 수, 쿨다운 → 총 거리·시간, 회차별 표 | 코스 길이에 들어가는지 확인, 진행 순서와 기록용 카드 내보내기 | 없음 |
| 2 | GPX·FIT·TCX 파일 도구 | 파일 → 거리·고도·끊긴 구간 확인, 자르기·반전·합치기·변환 | 이미 있는 가져오기·내보내기 코드를 활용하고 편집 지도로 보내기 | 없음 |
| 3 | 자전거 기어·케이던스 계산기 | 타이어 둘레, 앞뒤 톱니, 케이던스/목표 속도 → 기어별 속도·회전수 표 | 준비 중인 자전거 탭을 실제 도구로 채우기 | 없음 |
| 4 | 코스 기반 페이스 배분표 | 선택 코스, 목표 시간, 구간별 페이스 → 예상 통과 시각·전체 시간 | 기존 균일 페이스 스플릿에서 확장해 오르막·내리막·웨이포인트를 함께 보기 | 수동 입력판은 없음 |
| 5 | 대회 컷오프·출발 시간 역산기 | 출발 시각, 제한 시간, 체크포인트 거리/컷오프, 휴식 → 여유 시간과 필요한 평균 페이스 | 대회 코스와 체크포인트 웨이포인트 연결 | 없음 |
| 6 | 코스 비교기 | 저장된 두 코스 → 거리·상승·급경사·겹치는 구간 차이 | 회복 러닝/언덕 훈련 등 목적에 맞춰 사용자가 차이를 판단 | 없음 |

가장 먼저는 **인터벌·런워크 구성기와 자전거 기어 계산기**를 권한다. 입력과 결과가 명확하고 서버 호출 없이 만들 수 있으며, 기존 페이스 계산기와 쓰임이 구별된다. 파일 도구는 트라조와의 연결성이 강하지만 파일별 메타데이터·트랙 세그먼트·고도·시간을 어떻게 보존할지 먼저 정해야 한다.

### 1. 인터벌·런워크 구성기

예: `워밍업 10분 → 400m(4:30/km) + 회복 200m(7:00/km) × 6 → 쿨다운 10분`. 결과는 각 단계의 시간·거리, 총 운동 시간과 거리, 진행 순서 표다. 달리기/걷기 반복에도 같은 구조를 쓴다. 빠른/느린 구간을 여러 개 자유롭게 추가할 수 있고 화면 상태를 공유 링크로 보존하면 다시 방문할 이유가 생긴다.

첫 버전은 계산·복사·이미지 카드 내보내기까지만 구현할 수 있다. 시계용 구조화 운동 FIT 파일은 현재 **경로 FIT**와 다른 메시지 구조이므로 별도 기능으로 검증한 뒤 제공한다. 건강 상태를 추정해 훈련 강도를 자동 처방하기보다 사용자가 입력한 운동을 정확히 계산하는 것부터 시작한다.

### 2. 파일 도구

단순 변환은 기존 기능과 겹치므로, `기록의 앞뒤 잘라내기`, `서로 떨어진 두 파일을 합칠 때 단절 표시`, `시간·고도 없는 파일 확인`, `기기 업로드용 점 개수 줄이기`, `집 근처 시작·끝 지점 가리기`를 별도 가치로 삼는다. 가능하면 브라우저에서 처리하고 원본을 덮어쓰지 않는 다운로드 방식으로 만든다. 합친 구간을 실제 이동한 길인 것처럼 직선으로 몰래 연결하거나 없는 고도를 0으로 채우지 않는다.

### 3. 기어·케이던스 계산기

타이어 둘레와 기어비로 한 번 페달을 돌릴 때 이동하는 거리와 목표 속도의 케이던스를 계산한다. 바퀴 규격은 참고용 프리셋으로 제공하되 실측 둘레도 입력할 수 있게 한다. 바람·경사·출력을 추정하는 속도 예측과 달리 계산 관계가 명확하고, 로드/하이브리드/MTB 모두 사용할 수 있다. `내 자전거` 설정은 로그인 없이 브라우저에 저장할 수 있다.

### 4. 코스 기반 페이스 배분표

이미 있는 1km 균일 페이스 표와 구별하려면 사용자가 구간별 목표 페이스와 정차 시간을 넣고 전체 목표 시간에 맞춰 조정할 수 있어야 한다. 예를 들어 `급수 지점에서 1분`, `초반 3km는 느리게`, `복귀 구간은 걷기`를 코스에 표시한다. 첫 버전은 사용자가 정한 페이스로만 계산하고, 고도에 따른 자동 보정은 추정 모델·한계를 명시하며 나중에 추가한다. 3D 고도나 누적 상승만으로 정확한 완주 시간을 보장할 수는 없다.

## AI를 붙였을 때 가치가 있는 후보

| 아이디어 | AI의 역할 | 계산/검증 코드가 맡을 일 | 도입 조건 |
| --- | --- | --- | --- |
| 자연어 운동 구성 | “400m 6번, 회복은 200m, 준비·마무리 10분씩”을 편집 가능한 운동 단계로 변환 | 시간·거리 합계, 단위, 범위, 누락 확인 | 인터벌 구성기가 먼저 있어야 함 |
| 내 코스 기반 실행 계획 | 저장 코스의 오르막·웨이포인트를 근거로 사용자가 정한 목표의 구간 계획 초안 작성 | 실제 구간 길이, 휴식, 목표 시간 합계 검증 | 사용자가 코스와 목표를 명시하고 초안을 수정 가능해야 함 |
| GPX 문제 설명 도우미 | 감지된 점프·시간 역전·고도 누락을 일상적인 말로 설명하고 수정 방법 제시 | 이상 감지와 원본/수정본 비교 | 파일 도구가 먼저 탐지 결과를 구조화해야 함 |
| 대회 안내문 → 체크포인트 표 | 사용자가 붙여넣은 안내문에서 거리·운영 시간·컷오프 추출 | 단위·시각·날짜 검증, 누락을 사용자에게 확인 | 원문 근거를 항목마다 표시하고 확인 후 코스에 반영 |

기존의 코스 AI 리포트와 MCP 추천은 이미 있으므로 “AI가 코스 소개를 써 준다”는 별도 유틸리티의 차별점이 약하다. AI는 자연어·문서 해석을 맡고, 수치 계산·파일 변경은 코드가 수행하도록 나누는 편이 결과를 확인하기 쉽다. 기본 계산 도구는 로그인과 AI 호출 없이 제공하고 AI 보조 기능에만 요청 횟수 제한·비용 관리를 두는 구성이 적합하다.

## 진행 제안

1. `/utility` 러닝 탭에 **페이스 계산기 / 인터벌·런워크**를 추가하고 자전거 탭에 **기어·케이던스**를 제공한다.
2. 별도 `/utility/files`에 파일 점검·자르기·합치기를 제공하고 결과를 코스 편집기로 넘긴다.
3. 편집 코스의 `이 코스로 계획하기`에서 구간별 페이스·정차·컷오프를 계산한다.
4. 기존 입력 폼에 **자연어로 채우기**를 붙여 AI 기능을 도입한다. 합계와 파일 출력은 같은 계산 코드를 사용한다.

도구별 검색 주소·입력 예시·단위·결과 공유를 함께 설계하면 메뉴 안에만 있는 기능보다 발견하기 쉽다. 우선순위는 현재 코드 재사용과 기능 간 연결성을 기준으로 한 제안이며, 사용자 수요가 검증됐다는 의미는 아니다.
